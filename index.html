定位

给推荐架构后台工程师

02

命名

四个词指的是四件事

口语里的 transformer / transformers / vLLM / SGLang 经常被揉成一件事。学习时拆开，代码才对得上。

Transformer

一种神经网络结构。核心是注意力层。原始论文：Vaswani 等人 2017 年 Attention Is All You Need。

Transformers（库）

Python 库，仓库 huggingface/transformers。模型定义框架：配置、模型类、预处理器，加上 Pipeline 与 Trainer。

vLLM

推理与服务引擎，仓库 vllm-project/vllm。起源于 UC Berkeley；以 PagedAttention、连续批处理与 OpenAI 兼容服务闻名。docs.vllm.ai

SGLang

高性能 serving 框架，仓库 sgl-project/sglang。以 RadixAttention 前缀复用与结构化生成前端闻名。docs.sglang.ai / docs.sglang.io

和 checkpoint 的差别：架构是层的定义，checkpoint 是训练好的权重。「模型」两者都可能指。BERT 是架构，bert-base-cased 是一组权重。config.json 描述架构超参，权重文件才是 checkpoint。
03

迁移

推荐后台 ↔ 推理概念对照

把推理引擎想成「会说话的排序服务」：输入是 token 序列，输出是逐 token 生成；瓶颈常常在显存与调度，而不只是算力够不够。

推荐后台熟悉的概念LLM 推理中的对应备注
QPS / 吞吐throughput（req/s 或 tok/s）更常看 token/s；长输出时 req/s 会掉
p99 端到端延迟拆成 TTFT + 后续 token 延迟「多久开始吐字」与「吐字顺不顺」
批处理（mini-batch）continuous batching请求可中途加入、完成即离开
特征缓存 / Embedding 缓存KV cache；prefix / radix 缓存KV 在 GPU 上随序列与并发增长
分片 / 副本TP / PP / DP / EPTP 切权重；DP 像多副本抬吞吐
限流 / 熔断 / 排队max_num_seqs、队列、503、preemption显存不够会抢占重算
多租户 / 路由模型路由、LoRA、served-model-name网关 AB / 金丝雀与推荐一致
冷启动权重加载、CUDA graph / compile首次与重启后 TTFT 差一截
特征维 / 序列长度context length（max model len）超长上下文直接吃显存并抬 TTFT
一句话心智模型：推荐打分多为固定计算图；LLM decode 是自回归循环，历史 KV 常驻显存。并发越高、上下文越长，越容易撞显存墙。
04

结构

一块 Transformer 里有什么

原论文堆叠编码器与解码器块。今天的解码器-only LLM（GPT、Llama、Qwen）主要是「自注意力 + 前馈」反复堆叠，外加嵌入与输出头。

Token / Position Embedding把离散 token 变成向量
Multi-Head Self-Attention让每个位置从序列里取信息
Cross-Attention（编解码器才有）解码器读编码器的记忆
Feed-Forward Network逐位置非线性变换
残差 + LayerNorm / RMSNorm稳定训练与推理数值
LM Head投影到词表，采下一个 token

点上面的按钮，高亮当前要盯的子模块。

推理时「一次前向」就是：读已有 KV（若有）→ 算注意力与 FFN → 写出新 KV → 得到下一个 token 的分布。引擎要优化的，正是成千上万次这样的前向如何共享 GPU。

演示模型不是纯解码器堆叠。Qwen3.5-9B 的模型卡写明：32 层，排布是 8 ×（3 × Gated DeltaNet → FFN，再 1 × Gated Attention → FFN）。Gated Attention 才是上面这块全注意力；Gated DeltaNet 是线性递推，不按 token 增长 KV。先把经典注意力学扎实，再记住这张卡上的 9B 每 4 层只有 1 层在付全注意力的显存。
05

计算

缩放点积注意力

注意力让每个位置从其他位置收集信息。查询 Q、键 K、值 V 由输入线性投影得到。输出是值向量的加权和，权重来自查询与键的相似度。

Attention(Q, K, V) = softmax(QKᵀ / √dₖ) V

除以 √dₖ 防止维度变大时点积过陡。多头注意力把计算做 h 次再拼接投影。Vaswani et al., 2017

06

家族

编码器 / 解码器 / 编解码器

Encoder-only

BERT 一类。双向注意力，擅长理解与分类。推理引擎主战场通常不是它。

Decoder-only

GPT / Llama / Qwen。因果自注意力，自回归生成。vLLM / SGLang 的主战场。

Encoder–Decoder

T5 / BART。编码器读输入，解码器带交叉注意力生成。服务形态更复杂一些。

07

显存

KV cache 为什么贵

没有 KV cache，每生成一个新 token 都要对全部历史重算 attention。有了它，decode 只需读历史 K/V 并追加当前步。

  • 随序列长度线性增长（每层、每 token 存 K 与 V）
  • 随并发线性增长（每个 in-flight 请求一份）
  • 输出长度事先不知道，传统连续预留易碎片与浪费。vLLM 介绍博客称早期系统因碎片与过度预留浪费约 60%–80% 相关内存。vLLM 博客 2023
KV 示意：点 token 看「已缓存」格子

推荐类比：特征缓存若按「最大特征维 × 最大并发」整块预留会浪费；后面的 PagedAttention 像把缓存切成页按需分配。

KV 字节估算器（教学公式，非引擎实测）
—

公式示意：2 × L × H × d × S × B × bytes（K 与 V 各一份）。真实引擎还有分页对齐、Cuda graph、激活等开销；GQA/MQA 会改 H。以官方估算工具为准。

08

两阶段

Prefill 与 Decode

Prefill

整段 prompt 一次进模型，写满输入 token 的 KV。偏 compute-bound。决定 TTFT（多久开始吐字）。

Decode

逐 token 生成，复用并追加 KV。偏 memory-bound。决定 TPOT / ITL（吐字顺不顺）。

|---- Prefill（建 KV）----|======= Decode（逐 token）=======>
　　　　　　↑ TTFT　　　　　　　　　　↑ 每个间隔 ≈ TPOT / ITL
指标含义推荐类比
TTFT到首个输出 token首包延迟
TPOT每输出 token 平均间隔流水节拍
ITL词间间隔抖动敏感延迟
Throughputtok/s 或 SLO 内 req/sQPS（需声明 SLO）
压测须固定：模型、精度、长度分布、前缀是否共享、是否流式、硬件。公开榜若几乎无共享前缀，会低估 RadixAttention / prefix cache（见 Red Hat 文提醒）。
09

库

Hugging Face Transformers 做什么

Transformers 提供模型类、配置、tokenizer / processor，以及高层 pipeline 与训练循环 Trainer。它是「定义与加载模型」的框架，不是高并发服务运行时。官方文档

你常用的三件套

AutoConfig / AutoModelForCausalLM / AutoTokenizer，或对应的具体类。

落到磁盘

config.json + 权重（safetensors/bin）+ tokenizer 文件。vLLM / SGLang 读的就是这套布局（或兼容格式）。

10

体验

用 Transformers 做第一次生成

适合看清「tokenizer → 模型 → 下一个 token」这条接口。高并发交给第 17 节的推理引擎。

这段不要在单张 T4 上执行。Qwen/Qwen3.5-9B 的全精度权重，vLLM recipe 标成 BF16 约 22GB，对应单张 24GB 卡。T4 是 16GB，也没有 BF16 张量核。本机可执行的演示是第 17 节的 W4A16。
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

# 接口示意。16GB T4 上请不要 from_pretrained 这份全精度权重。
name = "Qwen/Qwen3.5-9B"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, torch_dtype=torch.float16, device_map="auto")

messages = [{"role": "user", "content": "用一句话解释 KV cache"}]
text = tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tok(text, return_tensors="pt").to(model.device)
out = model.generate(**inputs, max_new_tokens=64)
print(tok.decode(out[0], skip_special_tokens=True))

12

动机

为什么不能只用 model.generate

朴素实现的痛

  • 静态 batch：短请求被长请求拖死
  • KV 连续预留：碎片与浪费
  • 缺统一调度：GPU 空窗多
  • 缺生产 API：限流、流式、多租户要自己造

引擎补上的能力

  • Continuous batching
  • 分页 KV + 前缀复用
  • 张量并行 / 量化 / 推测解码
  • OpenAI 兼容 HTTP，方便接网关

vLLM 与 SGLang 都在做这件事，但起源优化点不同：前者先攻「装下更多请求」，后者先攻「相关请求少算重复前缀」（Red Hat 概括）。

13

vLLM 核心

PagedAttention：把 KV 切成页

vLLM 把每条序列的 KV 切成固定大小 block，物理上不必连续，用 block table 映射——类比操作系统分页。按生成进度按需分配，减少过度预留与碎片。介绍博客

内存实验室：连续预留 vs 分页

连续模式下，未用满的预留也会占格；分页模式只标记真正写入的块。颜色 A/B/C 表示不同请求。

分页式 KV 如今已成为现代引擎标配（SGLang 也采用同类思路）。vLLM 的差异化更多转向广模型 / 广硬件生态与工程完备度（见 Red Hat 2026-10-14 文）。

14

调度

连续批处理时间线

静态批处理：攒齐 N 条再算。Continuous batching：每 iteration 重新组 batch——新请求可插入，完成即离开。vLLM、SGLang、TensorRT-LLM 都以它为核心能力之一。

时间线实验室

看三条请求如何错开到达、在同一步共享 GPU，以及谁先结束离开 batch。

  • Chunked prefill：超长 prefill 切块，与 decode 交错，避免饿死正在吐字的请求。
  • Preemption：KV 不够时抢占并释放，之后重算。频繁抢占会伤延迟（vLLM Optimization 文档有说明）。
15

扩展

前缀缓存、量化、推测解码

Prefix caching

跨请求复用相同 prompt 前缀的 KV。vLLM 可配置开关；与 SGLang 的 Radix 是同一问题的不同实现重心。

量化

更低位宽存权重或 KV（FP8、W4A16 / AWQ / GPTQ 等），换显存与带宽，需业务验收质量。T4 不支持 FP8；这张卡的 9B 演示用 W4A16。

Speculative decoding

草稿模型提议、目标模型验证，加速 decode。以当前版本文档为准。

并行一句话：TP 切层内权重；PP 按层切；DP 复制模型抬吞吐；EP 切 MoE expert。

上手

vLLM 启动与关键旋钮

安装行来自 Qwen3.5-9B 模型卡（Qwen3.5 需要较新的 vLLM）。环境要求随版本变，落地前再看一次卡片。

uv venv --python 3.12 --seed
source .venv/bin/activate
uv pip install vllm --torch-backend=auto --extra-index-url https://wheels.vllm.ai/nightly

单张 T4 的起步用 RedHatAI/Qwen3.5-9B-quantized.w4a16：INT4 权重、激活保持原精度，给 vLLM 用。--language-model-only 与 --reasoning-parser qwen3 写在该仓库和模型卡的文本命令里。上下文从 8192 起步，是按 16GB 改短的，不是官方 262144。

vllm serve RedHatAI/Qwen3.5-9B-quantized.w4a16 \
  --served-model-name qwen3.5-9b \
  --reasoning-parser qwen3 \
  --language-model-only \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 1

curl http://localhost:8000/v1/models
8192、0.90、并发 1 是这张 16GB 卡的起步值，本页没有在 T4 上实测。先看 nvidia-smi 的剩余显存，再加长上下文或加大 --max-num-seqs。官方模型卡建议思考任务尽量保持至少 128K 上下文；那条建议在这张卡上做不到，思考质量会受短窗口影响。
配置作用推荐类比
--max-model-len上下文上限最大 payload
--gpu-memory-utilization显存占比（文档常见默认 0.92）内存水位
-tp张量并行卡数模型分片宽度
--max-num-seqs单步最多序列数最大并发
--max-num-batched-tokens单步 token 预算批配额；影响 TTFT↔ITL
prefix caching 开关前缀缓存公共特征缓存

对照：模型卡上的全精度文本命令，面向能放下 BF16（recipe 约 22GB）和 262144 上下文的机器。

vllm serve Qwen/Qwen3.5-9B \
  --tensor-parallel-size 1 \
  --max-model-len 262144 \
  --reasoning-parser qwen3 \
  --language-model-only
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY")
resp = client.chat.completions.create(
    model="qwen3.5-9b",
    messages=[{"role": "user", "content": "用一句话解释 KV cache"}],
    max_tokens=256,
    temperature=0.7,
    top_p=0.8,
    presence_penalty=1.5,
    extra_body={
        "top_k": 20,
        "chat_template_kwargs": {"enable_thinking": False},
    },
)
print(resp.choices[0].message.content)

非思考模式的温度来自模型卡的 Instruct 建议：temperature=0.7、top_p=0.8、top_k=20、presence_penalty=1.5。Qwen3.5 默认会先写思考过程；关掉它用 chat_template_kwargs.enable_thinking = false。模型卡写明不支持 Qwen3 的 /think、/nothink 软开关。

参数名与默认值请以 vllm serve --help 与 Optimization 页为准。频繁 preemption → 提高 utilization、降并发。这张机器只有一张卡，TP 保持 1。
18

SGLang 核心

RadixAttention：跨请求前缀复用

SGLang（Structured Generation Language）是面向 LLM 与多模态的高性能 serving 框架。后端核心 RadixAttention：请求结束后不立刻丢弃 KV，而把 token 前缀索引进 radix 树；新请求做最长前缀匹配，命中则只算后缀。LMSYS 博客

前缀树示意

共享 system prompt 的多会话，会在树的上层节点命中（高亮）。这是 agent / 多轮 / few-shot 场景的收益来源。

维度vLLM（起源重心）SGLang（起源重心）
KV 分配PagedAttention 降碎片高效分页 + radix 索引
跨请求复用Prefix caching（可配置）RadixAttention 自动前缀复用
前端OpenAI API / 引擎参数OpenAI API + 结构化生成 / DSL 传统
今日两边都在吸收对方能力；选型看负载与生态，而非 2023 标签

物理 KV 仍在 GPU 分页存放；Radix 解决「如何发现并复用前缀」，PagedAttention 解决「如何高效分配单请求 KV 页」——互补。

  --context-length 262144 \
  --reasoning-parser qwen3
单张 T4 不要照抄 262144 和全精度仓库。这张卡先把第 17 节的 vLLM W4A16 跑通。SGLang 实验把 --context-length 降到能启动的值（可从 8192 试）。若当前版本加载不了这份混合架构或 W4A16，把报错原文留在周记里。模型卡对照表里的 Qwen3.5-4B 可以用来把前缀实验做完；那是另一条显存预算，延迟不要和 9B 画在一起。
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY")
resp = client.chat.completions.create(
    model="Qwen/Qwen3.5-9B",
    messages=[{"role": "user", "content": "用一句话解释前缀缓存"}],
    max_tokens=256,
    temperature=0.7,
    top_p=0.8,
    presence_penalty=1.5,
    extra_body={
        "top_k": 20,
        "chat_template_kwargs": {"enable_thinking": False},
    },
)
print(resp.choices[0].message.content)

  2. 预热后测稳态 TTFT

落地

对接网关与监控最小集

  • 网关只改 base_url / api_key，走 OpenAI Compatible
  • 超时分层：连接超时、首 token 超时（TTFT SLO）、总超时
  • 重试只对可安全重试错误；注意流式中途失败
  • SSE 给到端；反向代理注意缓冲与 idle timeout
  • 限流：租户 QPS、token 预算、按模型
  • 路由 / A/B：served-model-name 或网关键

监控最小集

TTFT、TPOT/ITL、端到端延迟、队列长度、GPU util、显存、preemption 次数、缓存命中率（若有）。

现象常见原因方向
OOM模型+KV 超显存；上下文过大降 max-model-len / 并发；量化；加 TP
TTFT 变差长 prefill、排队、冷启动、缓存未命中chunked prefill、限流、预热、稳定前缀
ITL 高batch 混入大块 prefill；并发过高调 batched tokens；优先 decode
多轮越聊越慢上下文变长，KV 膨胀截断 / 摘要；前缀缓存

路线

4–6 周学习路线 + 练习六件事

周 1 · 概念对齐

讲清 prefill/decode、KV、continuous batching、TTFT/TPOT。读 Qwen3.5-9B 模型卡的层排布：32 层里只有 1/4 是全注意力。画出 16GB 预算：BF16 约 22GB 放不下，演示走 W4A16 文本。

周 2 · 在 T4 上跑通 vLLM

按第 17 节拉起 W4A16，language-model-only，上下文从 8192、并发从 1 起步。先打一条 enable_thinking: false 的短请求，确认 OpenAI 接口。

周 3 · 这张卡的压测

固定短 prompt，并发只扫 1、2、4。记录自己的 TTFT 与是否 preemption。上下文加长前先看剩余显存。不把官方 128K 思考窗口当作这张卡的目标。

周 4 · 前缀复用

共享一条长 system prompt，只改 user。vLLM 看 prefix caching；SGLang 能启动再看 radix。加载的若是 Qwen3.5-4B 或其他权重，单独画图，不和 9B 的延迟比。

周 5 · 同一张 T4 上选型

两引擎都用实际能加载的 checkpoint、同一批短请求。一页纸写明模型名、量化、上下文、引擎版本。读 Red Hat 全文与 Baseten §4.3。

周 6 · 进阶（可选）

打开一次思考模式，把 max_tokens 限制住，对比非思考的总长度。再写网关超时与 OOM 手册。多卡 TP 留到有第二张卡；换 24GB 卡时再考虑 BF16 和更长上下文。

练习六件事（可打卡）

  1. 口述注意力公式，并说出 Qwen3.5-9B 每 4 层里只有 1 层是全注意力
  2. 用估算器感受 KV 随并发/长度膨胀，对照 T4 的 16GB
  3. 在 T4 上用 W4A16 拉起 vLLM，非思考模式打通一次 chat completions
  4. 同一服务再开一次思考模式，限制 max_tokens，对比回复长度
  5. 构造高前缀重叠流量，对比缓存开/关，并写上实际加载的模型名
  6. 写一页「16GB 怎么分给权重和 KV」以及告警阈值草案
每周五输出一页纸（指标图 + 结论 + 下周问题）。验收附引擎版本、GPU、完整启动命令。

问答

推荐同学常问

Q. 我们该先上 vLLM 还是 SGLang？

两周内要稳妥上线通用开源模型 → 多数团队先 vLLM。流量明显共享 system/工具定义 → 必须认真测 SGLang。最终用自家回放数据说话。

Q. slang 是另一个项目吗？

口语里通常就是 SGLang。若有人指别的缩写，让对方给出仓库链接再对齐。

Q. 和排序服务共用 GPU 行吗？

技术上可能，运维上很痛：KV 膨胀会挤占，延迟抖动互相放大。生产更常见是推理池独立，经网关调用。

Q. 为什么榜单和我压测差很多？

长度分布、前缀重叠、是否流式、精度、是否默认配置都不同。无共享前缀的榜会低估 radix/prefix。

Q. OpenAI SDK 能直接打两家吗？

可以。改 base_url 与 model 名即可。注意 chat template / tool call 细节仍可能有差异，以各引擎文档为准。

Q. 模型卡写了 262144，这张 T4 为什么用 8192？

262144 是 Qwen3.5-9B 的原生上下文，模型卡还建议思考任务尽量保持至少 128K。vLLM recipe 把 BF16 放在约 22GB、单张 24GB 卡上。T4 是 16GB，且不支持 FP8。全精度和长上下文会在加载权重或分配 KV 时失败。这张卡用 W4A16 文本权重，上下文从 8192 往上试。

Q. 第一次请求为什么关掉思考？

Qwen3.5 默认先写思考再回答，短问题也会吐出很长的 reasoning，把 8192 的窗口和 T4 的剩余显存吃掉。打通接口时用 enable_thinking: false。确认服务稳定后，再单独开一次思考，并限制 max_tokens。
