02

命名

四个词指的是四件事

口语里的 transformer / transformers / vLLM / SGLang 经常被揉成一件事。学习时拆开，代码才对得上。

Transformer

一种神经网络结构。核心是注意力层。原始论文：Vaswani 等人 2017 年 Attention Is All You Need。

Transformers（库）

Python 库，仓库 huggingface/transformers。模型定义框架：配置、模型类、预处理器，加上 Pipeline 与 Trainer。

vLLM

推理与服务引擎，仓库 vllm-project/vllm。起源于 UC Berkeley；以 PagedAttention、连续批处理与 OpenAI 兼容服务闻名。docs.vllm.ai

SGLang

高性能 serving 框架，仓库 sgl-project/sglang。以 RadixAttention 前缀复用与结构化生成前端闻名。docs.sglang.ai / docs.sglang.io

和 checkpoint 的差别：架构是层的定义，checkpoint 是训练好的权重。「模型」两者都可能指。BERT 是架构，bert-base-cased 是一组权重。config.json 描述架构超参，权重文件才是 checkpoint。

迁移

推荐后台 ↔ 推理概念对照

把推理引擎想成「会说话的排序服务」：输入是 token 序列，输出是逐 token 生成；瓶颈常常在显存与调度，而不只是算力够不够。

结构

一块 Transformer 里有什么

原论文堆叠编码器与解码器块。今天的解码器-only LLM（GPT、Llama、Qwen）主要是「自注意力 + 前馈」反复堆叠，外加嵌入与输出头。先拖图，数字和名字都标在图上。

整个模型的一次前向与采样 · 拖动查看 1 / 6

整模型先查 Embedding，再经过多个 Decoder Block，最后经 Norm 与 LM Head 得到 logits；采样才选出新 token。Embedding 与 LM Head 不在每个 Block 里重复。引擎优化这些前向与请求如何共享 GPU。

单个常见 Pre-Norm Block 内部位置与作用
Norm → 注意力 → 残差相加Q/K/V 来自本层输入；RoPE 在 Q/K 上引入位置旋转
Norm → FFN → 残差相加逐位置变换；另有这一条残差支路

这是常见解码器结构的教学骨架，不是 2017 Post-Norm 的逐行实现，也未展开 Qwen 的 gate。Qwen3.5 的 GDN 层要用递推状态替代普通全注意力的 KV 历史；下面单独画出层排布。

05

计算

缩放点积注意力

注意力让每个位置从其他位置收集信息。查询 Q、键 K、值 V 由输入线性投影得到。输出是值向量的加权和，权重来自查询与键的相似度。

Attention(Q, K, V) = softmax(QKᵀ / √dₖ) V

除以 √dₖ 防止维度变大时点积过陡。多头注意力把计算做 h 次再拼接投影。Vaswani et al., 2017

拖动查询位置 · 格子里的数是当场算的

把上面选中的那一行拆成五步

同一组二维 Q、K，再给每个位置一个二维 V。从左到右每一列是一步，铜色是当前这一步。最后一行是输出向量，也就是这个位置交给下一层的注意力结果。

因果掩码：解码器-only 生成时，位置 i 只能看见 ≤ i 的 key。这就是「从左到右吐字」的数学来源。Decode 时新位置本来就排在最后，只有一行 q，不需要额外再画掩码。

多头与 GQA：为什么 KV 头比 Q 头少

多头注意力把同一层拆成多组 Q、K、V 各算一遍。Qwen3.5-9B 的全注意力层有 16 个 Q 头，但只有 4 个 KV 头：每 4 个 Q 头共用一组 K、V。这叫 GQA（Grouped-Query Attention）。KV cache 只存 KV 头，所以每层每个 token 是 2 × 4 × 256 × 2 字节 = 4 KiB；如果 16 个头各存一份就是 16 KiB。

05A

把链路串起来

从 token id 到下一个 token

Token 不等于一个汉字或一个单词。Tokenizer 把字符串切成词表中的 token id；chat template 把 system/user/assistant 角色与控制符序列化。前缀缓存比较的是这些实际 token 的连续前缀，不是语义相似度。

数据普通批次形状含义
input_ids[B, S]B 个序列，每条 S 个已知 token
hidden states[B, S, D]查表并逐层变换后的向量
Q[B, Hq, S, d]各注意力头的查询
K / V（普通 GQA）[B, Hkv, S, d]KV 头可少于 Q 头，因此计算器用 Hkv
logits[B, S, Vocab]每个位置预测其后一个 token 的分数；引擎可只算需要的位置

生成下一个 token 时取最后位置的 logits，经过温度、top-k/top-p 等采样规则选出一个 id，再送回下一次前向。LM Head 产生分数，softmax/采样形成选择；它不是直接拼出一句话。

采样实验室：同一组 logits，换参数看谁会被选中

题目：「KV cache 主要占用的是 ___」。8 个候选和 logits 是编的，词表真实有 248320 项。浅色条是只除以温度后的概率，绿色细条是截断、重新归一化之后真正参与抽样的概率，黑色竖线是最近 200 次抽样的频率。

顺序：先把 logits 除以温度再 softmax；top-k 只留分数最高的 k 个；top-p 在剩下的候选里按概率从高到低累加，够 p 就停；最后重新归一化再抽。这里按 Hugging Face 的 warper 顺序演示，各引擎的实现细节以文档为准。Qwen3.5 模型卡给非思考模式的建议是 T = 0.7、top-p = 0.8、top-k = 20；本例只有 8 个候选，所以 top-k = 20 不起作用。温度只改变分布的尖锐程度，不改变排名。

固定 seed 只固定随机数。同一个请求单独跑和混在别的请求里跑，内核的分块和累加顺序可能不同，浮点结果就可能差一点。DeepSeek 的 DeepInfer（生产引擎，T4 跑不了，见第 20 节）把「批不变」做成单独的开关（只在 NVIDIA 上）；确定性采样还要每条序列固定 seed，并关掉按整批分配的变长验证（第 15 节）。

为什么不缓存 Q？普通因果自注意力生成后续 token 时，用新的 Q 查询已有 K/V；过去的 Q 不参与这个新位置的计算。每层缓存自己的 K/V。GDN 则保留卷积与递推状态，不逐 token 保留完整 K/V 历史。

不使用 KV cache 的朴素循环会重复计算历史位置的投影、注意力和 FFN；使用 cache 后，decode 仍需读取历史 KV 做注意力，不是「旧 token 完全不再计算」。形状、移位预测与可选的 Qwen3.5 前向观测见 原理补充。

控制 token 只该由模板插入。chat template 插进去的 <|im_start|> 这类控制符是 special token。常见流程先把整段对话渲染成字符串、再整串 tokenize，用户正文里敲出的同样拼写也会被编成控制 token：用 Qwen3.5-9B 的 tokenizer 试，一轮消息本该有 3 个控制 token，正文里写两段拼写就变成 5 个（不用 GPU 的几行代码见原理补充）。DeepSeek 开源的 deepseek-recipe 在拼 prompt 时记下模板插入控制 token 的区间，只有这些区间按 special 编码，其余正文按普通文本编码；输出方向也只认 token 形式的 </think>。控制 token 还把 prompt 切成互不影响的几段，可以并行 tokenize，长上下文的分词延迟随之下降。DeepInfer Q&A

06

家族

编码器 / 解码器 / 编解码器

Encoder-only

BERT 一类。双向注意力，擅长理解与分类。推理引擎主战场通常不是它。

Decoder-only

GPT / Llama / Qwen。因果自注意力，自回归生成。vLLM / SGLang 的主战场。

Encoder–Decoder

T5 / BART。编码器读输入，解码器带交叉注意力生成。服务形态更复杂一些。

名字里带 encoder-decoder 的因果模型。DeepSeek-V4.1-Flash 的 Causal Encoder-Decoder（CED）不是 T5 那种编解码器，整个模型仍按因果自回归生成：40 层里前 20 层叫 encoder，后 20 层 decoder 的全局 KV 从 encoder 最后一层投影出来，所以 prefill 每 token 只激活 8B 参数，decode 激活 16B。不同在缓存怎么存、prefill 要算哪几层，见第 7、18 节。模型卡
07

显存

KV Cache 的账：存什么、怎么涨、何时还

对于普通因果注意力，不带 cache 的朴素生成循环会反复处理全部历史。有了 cache，decode 只计算新输入位置的投影与层变换，并用新的 Q 读取历史 K、V。KV 缓存不等于完整回答缓存。这一节按 Datawhale《zero-to-sglang》第 4 章「推理的核心数据结构」的问题来写：缓存从哪来、一次请求怎么用它、显存怎么估算、多请求时连续分配为什么撑不住。手算矩阵和章末题在原文，本页不转载正文。

留下的是每层的 K 和 V

进注意力之前，当前位置的隐藏状态各自乘出 Q、K、V。Q 表示这一步想从上下文里取什么，K 是每个历史位置用来打分的特征，V 是被加权汇总的内容。各层权重不同，所以每一层各存各的。

  • Prefill：整段 prompt 一次算出全部 token 的 Q、K、V，把每层的 K、V 写进这条请求的缓存，再做带因果掩码的注意力。预测第一个新 token 只用最后一个位置的隐藏状态。
  • Decode：采样得到的是 token id。下一步把这个 id 重新 embedding，再投影出本步的 q、k、v，把 k、v 接到历史缓存后面。q 和全部 K 做注意力，再对全部 V 加权。Q 用完即弃，下一步不会复用它。
  • 注意力之后，这个新位置还要走输出投影、残差、归一化和 FFN。整层走完，最后一层隐藏状态进 LM Head，得到词表上的 logits。
  • 随序列长度线性增长（每层、每 token 存 K 与 V）。无共享时随活跃序列数近似线性增长；前缀共享、滑动窗口与混合状态会改变实际分配。
和激活的差别：中间激活算完就可以复用那块显存。KV 要跨过后面的每一个 decode step 留着，并按层、按 token 增长。所以长上下文和多请求并发时，KV 会从「比权重小」变成显存的大头。

默认是 Qwen3.5-9B 模型卡上的全注意力：8 层、4 个 KV 头、头维 256。公式 2 × L × nkv × d × tokens × B × bytes 只算这些层的 K 和 V。容量基准默认 15 GiB，贴近 T4 上 nvidia-smi 常见的可见容量，请改成自己的读数。临时工作区、缓存池对齐和 CUDA Graph 都不在公式内，理论合计也不等于实测峰值。长度默认相同；真实请求要用各请求长度之和。

另外 24 层 GDN 每条序列各有一份固定大小的状态。按 config.json，每层递推状态是 32 个 V 头 × 128 × 128，卷积状态是 (16×128×2 + 32×128) × 3。config 里写了 mamba_ssm_dtype: float32，vLLM v0.18.1 会照此把递推状态存成 FP32，卷积状态跟随模型 dtype（这里 FP16）。合起来每层约 2.05 MiB，24 层约 49.1 MiB。它不随上下文变长，但每多一条并发序列就多一份。所以短对话时，GDN 状态比那 8 层 KV 还大。--mamba-ssm-cache-dtype float16 可以减半，vLLM 会打印警告，对输出质量的影响要自己验收。

要复用前缀，这份滚动状态必须在块边界上留检查点。下一条请求要从第 i 个 token 接着算，就得有那一层当时的 GDN 状态，而不只是 8 层全注意力的 K、V。align 只在某次调度步刚好结束在块边界时，保存这一步最后一个 token 的状态。APC 也只缓存写满的块，所以两边是同一条边界，命中长度是块大小的整数倍。none 不为复用保存检查点；关掉前缀缓存时就是它。在 v0.18.1 上，前缀缓存开着且模型支持时，默认常常是 all：在每个块边界都存 GDN 状态。这是这一版的正常选择，不是日志打错；实验把模式原文抄下来。v0.32 起去掉了 all。要带走的模型是：开着 APC 用 align，关掉用 none。命中是不是整块，两种版本都用这一条判断。v0.18.1 cache 配置

定长状态放哪，有两种做法。vLLM 0.18.1 只有一个页池，所以页被撑大到能装下一份 GDN 状态（第 13 节的 528 token）。DeepSeek 的 DeepInfer 用两个分配器：会增长的压缩 KV 按 128 token 一块分页；滑动窗口（128）的 KV 和压缩累加器放进每条序列一个的定长槽，槽数启动时就切好，接纳请求时两边都要分得出来。环形缓冲是窗口 128 再加 6 格，留给投机解码回退，因为被拒的草稿已经写进了环。一个池子共用容量但页大；两个池子页小，代价是定长状态那份显存要预先切走。

权重 9.35 GiB 是把固定 revision 的 W4A16 checkpoint 里语言模型部分的张量逐个加起来得到的（不含视觉塔与 MTP）：FFN 与全注意力是 4bit，24 层 GDN 的线性层、Embedding、LM Head 仍是 16 位。T4 上 15 GiB × 0.85 的预算里，留给 KV、GDN 状态与激活的大约只有 3.4 GiB。

低精度 KV 压的是公式里的「字节/元素」，不是权重。从 2 改成 1，同样的上下文少搬一半历史。Decode 吃带宽时，这换上下文长度和逐步延迟，同时要验收质量，还要有这块 GPU 上的内核。T4 实验把 --kv-cache-dtype 留在 auto，跟随 FP16，避免和 W4A16、GDN 搅在一起。在更新的服务里，FP8 KV 可以是某些模型在高端 GPU 上的默认，例如 v0.32 说明里 GLM-5.x 在 SM100 上默认 FP8 KV；NVFP4 和 4-bit KV 是可选项，不是这些模型的默认。日志里要分开看的三件套始终是：权重 dtype、KV dtype、GDN 递推 dtype。

存储精度不等于计算精度。DeepSeek-V4.1-Flash 在自家栈里把主压缩 KV 默认存成 FP4（每 16 通道一个 E4M3 scale）、滑窗 KV 存 MXFP8，全局 KV 约 890 字节/token；它的 FLOPs 估算器仍把注意力记成 BF16 运算。这套格式是模型、内核和 SM100 一起定的，T4 没有 FP8/FP4 张量核，抄不过来。你的 W4A16 是同一个道理：INT4 省的是搬运的字节，矩阵乘照样按 FP16 算。FLOPs 估算器 · 模型卡

对一下原文例题：把 L、KV 头、头维、T、l、B 改成 36、8、128、100、0、1，字节选 BF16，GDN 层数改成 0（那是纯全注意力模型）。Prefill 与「再生成 l 个之后」都应约为 14.06 MiB，每步新增显示 144.0 KiB（约 0.14 MiB）。滑条从 256 起步，这一题改数字框；再拖滑条会把 T 吸到 256 的倍数。那一章用的是 Qwen3-4B-Thinking-2507，不是本页默认的 9B。

一次请求的生命周期

  1. 分配。为这条请求准备可写的位置。引擎里的单位是固定大小的 block / page，按生成进度领取。
  2. Prefill 写入。prompt 每个 token 的 K、V 按层写入。前缀已经在缓存里时，命中的那段可以跳过重算。
  3. Decode 读取并追加。每步读历史 K、V，只把新 token 的 K、V 接上去。Q 不进入缓存。
  4. 结束。遇到 EOS、长度上限或取消，就减少这些页的引用计数。降到 0 归还 GPU 上的空闲池。开了前缀缓存或 RadixAttention 时，后来的请求还能命中的页会继续被引用，直到按策略淘汰。

多请求时，连续大数组为什么不够

单请求用一块连续张量存 KV，分配和追加都好讲。在线服务里请求长度和寿命都不一样，还要中途加入、完成离开。这时仍按请求划一块连续显存，会碰到四件事：

碎片和预留

按最大上下文预留，没生成的 token 先占住显存。动态分配又会留下对不上的空洞。连续区域要扩容时，还可能重新分配并拷贝。vLLM 介绍博客称早期系统因此浪费约 60%–80% 相关内存。vLLM 博客 2023

前缀存了多份

多条请求常带同一段 system prompt。各自一块缓存，就会重复保存同一段 K、V。公共前缀越长，重复占用越大。

调度和回收绑在一起

加入、退出、抢占、恢复都要同时改容量、地址和优先级。缓存一分散或需要搬家，元数据开销就上来了。

和连续批处理打架

每一步都要能插入新请求、移除已完成请求。若内核只吃规整的矩形张量，就要按最长序列填充；若为了紧凑而重排，就要 gather 或搬移。

所以 KV 不能只当成「每条请求一块越长越大的连续张量」。第 13 节的 PagedAttention 把页按需映射；第 18 节的 RadixAttention 再把相同前缀收成一棵树。物理页仍在 GPU 上，两件事解决的是不同问题。

两阶段

Prefill 与 Decode

一次请求 · 拖动查看前向次数

Prefill

处理 prompt 的所有新位置（可分 chunk），写入其 KV；最后一个位置的 logits 可采样出首个新 token。长 prompt 通常偏 compute-bound，是 TTFT 的一部分。

Decode

普通自回归每步输入上次采样的 token，计算它的 KV 并预测下一个。小 batch 常偏 memory-bound，涉及权重与 KV 读取；大 batch 与不同架构可能改变瓶颈。

图中 4 个 prompt 位置在第一次前向统一处理，同时得到首个新 token；新 token 自身的 KV 在下一次前向才计算。动画只表示先后顺序，不表示各阶段耗时相同。客户端 TTFT 还包含网络、排队、预处理与回传；ITL 是 token 间隔，TPOT 是请求级平均，不能把任意 SSE 分块当成单个 token。

下一步的输入是 token id。Prefill 用最后一个位置的隐藏状态选出第一个新 token。Decode 再把这个 token id 做 embedding，投影出新的 q、k、v，只把 k、v 追加进第 7 节的缓存。上一步的隐藏状态不会被原样送回模型。

为什么 Prefill 吃算力、Decode 吃带宽：在 T4 上算一遍

GPU 每一步既要算（FLOPs），也要把权重和缓存从显存搬进计算单元（bytes）。两者之比叫算术强度。T4 规格标称 FP16 张量核 65 TFLOPS、显存带宽 320 GB/s，两者相除约 203 FLOP/byte，这是「屋顶线」的拐点：强度低于它，时间花在搬数据上；高于它，时间花在算上。

线性层每处理 1 个 token 约做 2 × 参数量 次浮点运算，但权重每一步只需从显存读一遍，能被这一步里的所有 token 共用。Decode 一步里每条序列只有 1 个新 token，B 条并发也只有 B 个；Prefill 一步里有成百上千个 prompt token。瓶颈不同的根源就在这里。推荐后台的类比：decode 像每次只查一个 key 却要扫一遍整表，批量查询才能把扫表成本摊薄。

两段时间，和两种机器形态

长 prefill 偏算力，小 batch decode 偏带宽。挤在同一次调度里时，一个长 prompt 会把正在吐字的请求的 token 间隔拉长。T4 上能看到的是：max-num-seqs=1 时后来的请求只能排队；调高之后，chunked prefill 让 prefill 和 decode 共享同一步。同时记下 TTFT 和逐步间隔，看变的是哪一项。

把 prefill 和 decode 放到不同实例，是同一冲突的多机形态。prefill 池对着 TTFT，decode 池对着每人每秒 token，代价是把算好的 KV 送过去。收益出现在重算这段 prompt 比搬走 KV 更贵的长输入上。SGLang 在长 prompt 的 PD 负载上报告过吞吐最多增加 27%、p95 TTFT 降到约一半；那是他们的测量，单张 T4 拆不开。出处

生产里的 PD 还配着不同的并行尺度。DeepSeek 的 V4.1-Flash 用常见的 8 卡机做 prefill（专家并行 EP 2–8，显存够就尽量小），用 64–128 卡的超节点做 decode（Wide-EP，越宽越好），P、D 卡数约 1:1，KV 放独立存储。搬 KV 的成本跟 KV 大小直接相关：全局 KV 压到约 890 字节/token 后，P、D 分在相邻的两个机房也搬得动（大约每 8 张卡配 400 Gbps）。decode 的负载均衡同时看每张卡的请求数和 KV 总长，正好是上面屋顶线的 B 和上下文两个滑条；prefill 给每一步一个时间预算，用拟合的代价模型（新 token 数、已算前缀长度）反解 chunk 大小，而不是固定 token 数。DeepInfer Q&A

更早还有一段等待：权重从磁盘进 GPU，到服务就绪为止。它不是请求的 TTFT。本实验会为了只改一个变量而反复重启，所以要把这段墙钟时间单独记下。SGLang 的 InstantTensor 加载器针对这一段；项目称大约快 10 倍，同页例子是 DeepSeek-R1、8×H200、50 GB/s 存储，从 160 s 到 15.3 s。不是 Qwen3.5-9B，也不是 T4。

屋顶线没算 kernel 启动和卡间通信。一个用户、或推测解码一次只验证几行 token 时，每颗 kernel 的算术很少，时间花在等待上一颗写完，以及 all-reduce 上。高端 GPU 上的低延迟内核用依赖启动提前拉起下一颗 kernel，并把 all-reduce 叠进 GEMM 的收尾；也有把一整层收成一两次常驻 kernel 的做法。需要专用内核，T4 实验不跑。和第 14、15 节一起看。

动机

为什么朴素 model.generate 封装还不够

朴素实现的痛

  • 固定 batch：完成的槽位难以及时补入新请求
  • 朴素 KV 预留策略可能导致碎片与浪费
  • 缺统一调度：GPU 空窗多
  • 缺生产 API：限流、流式、多租户要自己造

引擎补上的能力

  • Continuous batching
  • 分页 KV + 前缀复用
  • 张量并行 / 量化 / 推测解码
  • OpenAI 兼容 HTTP，方便接网关

这四项正好对应第 7 节的连续 KV：预留浪费、前缀重复、回收复杂、变长请求难拼成矩形 batch。这里比较的是朴素封装，非 Transformers 今天全部能力。vLLM 与 SGLang 的起源优化点不同：前者先攻「装下更多请求」，后者先攻「相关请求少算重复前缀」（Red Hat 概括）。

vLLM 核心

PagedAttention：把 KV 切成页

第 7 节里那块随序列变长的连续 KV，在这里被切成固定大小的 block。物理上不必连续，用 block table 映射——类比操作系统分页。按生成进度按需分配，减少过度预留与碎片。介绍博客 · vLLM 文档

内存实验室：每格一页，每页 4 个 token

块表（block table）：每条请求一行，左边是逻辑页号，右边是它落在哪个物理页、写了几个 token。Decode 时注意力 kernel 按这张表逐页去读 K、V，所以物理页散在各处也没关系。

连续模式下，未用满的预留也会占格；分页模式只标记真正写入的块。颜色 A/B/C 表示不同请求。

分页之后仍有两类浪费：每条请求最后一页没写满（内部碎片，平均约半页）；以及被前缀缓存留着、暂时没人用的页（可被淘汰）。多条请求共享同一段前缀时，可以让各自的块表指向同一批物理页，用引用计数管理；有人要在共享页上继续写时，再复制一份（copy-on-write）。

在你的 9B 上，一页不是 16 个 token。vLLM 默认块大小是 16，但 Qwen3.5 是混合模型：这一页还要放下 GDN 状态检查点（递推部分按 config 存 FP32，约 2.05 MiB）。检查点不随 token 变小，所以块被调大。按 v0.18.1 源码，不开前缀缓存时块大小 = 16 × ⌈2.05 MiB ÷ (16 × 4 KiB)⌉ = 528 个 token；开了前缀缓存还可能按内核要求再调，改用 FP16 状态则约 272。启动日志里的「Setting attention block size to N tokens」就是复用粒度。v0.18.1 开着前缀缓存且模型支持时，默认常常是 all，把原文抄下。v0.32 起开 APC 用 align，检查点落在写满的这一页上；关掉用 none。命中长度是 N 的整数倍（第 7、18 节）。块越大，尾页碎片越大。

分页式 KV 如今已成为现代引擎标配（SGLang 也采用同类思路）。vLLM 的差异化更多转向广模型 / 广硬件生态与工程完备度（见 Red Hat 2026-10-14 文）。v0.18.1 混合 KV 缓存设计

调度

连续批处理时间线

固定批处理：组好的一批通常一起推进，完成的槽位不及时补入新请求（不要求永远等满 N 条才启动）。Continuous batching：在调度步边界重组 batch——新请求可加入，完成即离开，并不是在一个 GPU kernel 运行到一半插入。vLLM、SGLang、TensorRT-LLM 都以它为核心能力之一。

同样 7 条请求、4 个槽位：静态批 vs 连续批

每一列是一次调度步（一次前向），每一行是一个槽位，相当于 max-num-seqs = 4。粗体 P 是这条请求的 prefill，那一步同时得到首个 token；后面每格吐 1 个 token。虚线格是空转的槽位，最下面一行是已经到达、还在排队的请求。为了看清调度，这里把 prefill 画成 1 步。

  • Chunked prefill：超长 prefill 切块，与 decode 交错，避免饿死正在吐字的请求。
  • Preemption：KV 不够时抢占并释放，之后重算。频繁抢占会伤延迟（vLLM Optimization 文档有说明）。

小 batch 的延迟，和吞吐内核不是同一类优化

第 8 节的屋顶线：并发从 1 往上加，读权重的成本被摊薄，总吞吐上升，单条请求的逐步时间几乎不变，直到 KV 读取或算力追上。吞吐内核按这个方向做大 tile、一次喂很多 token。延迟内核对着相反的角：一个用户，或推测解码一次只验证几行，kernel 太小，GPU 在两次启动之间空等。

依赖启动（programmatic dependent launch，PDL）让下一颗 kernel 在输入还没就绪时就启动，先摆好屏障、装上权重，真正用到数据时再等。张量并行里，GEMM 算完一块就把部分和发给对端，通信叠在后面几块的计算上，而不是等整颗 GEMM 写回显存再另起一颗 all-reduce。AMD 上的 monokernel 更进一步：一层里几十个小 kernel 收成两次常驻启动，all-reduce 做在核内。LMSYS 低延迟内核把这两类做成插件（NVIDIA 的 sgl-nvidia-mega、AMD 的 sgl-amd-mono），服务的是 DeepSeek-V4.1-Flash 加 DSpark。文中 AgentX 回放、与同硬件基线相比：四张 GB300、1 路并发，P90 每用户生成速度从 671.2 tok/s 到 928.4 tok/s（1.38×）；四张 MI355X、4 路并发，从 331.6 tok/s 到 516.0 tok/s（1.56×）。需要这类 GPU 和专用内核，T4 实验不跑。

T4 上对应的观察在并发实验里：同时记下 TTFT 和 token 间隔。并发升高后若 TTFT 变差、间隔几乎不变，你看到的是排队和 prefill 干扰。单卡上的这点干扰，就是多机上把 prefill、decode 拆开要消除的那件事。

CPU 也会让 GPU 空等：异步调度

每一步 decode 是「调度 → 前向 → 采样 → 后处理」。调度和后处理在 CPU 上，后处理前还要等采样结果拷回来，这段时间 GPU 空着。异步调度把它们错开一步：GPU 跑第 N 步时，CPU 已经排好并发出第 N+1 步，同时处理第 N−1 步的输出。代价是 CPU 看到的长度落后一步，引擎要先按乐观长度占位、再在 GPU 上修正，发射路径里不能有 CPU-GPU 同步。DeepSeek 的 DeepInfer 直接用 torch.cuda.set_sync_debug_mode("error") 守住这条路径，它的 Q&A 说做法参考了 SGLang 和 Nanoflow。vLLM 0.18.1 默认开启，启动日志有 Asynchronous scheduling is enabled.。收益看一步多长：T4 上 9B 一步至少约 25 ms，CPU 占比小；一步只有几毫秒的高端部署才最需要它。实验第 7 步可以用 ASYNC_SCHED=0 关掉对照，第 9 步的 --sync-debug 能看到朴素循环每一步在哪里等 GPU。v0.18.1 源码 · DeepInfer worker

扩展

前缀缓存、量化、推测解码

Prefix caching

跨请求复用相同 prompt 前缀的 KV。vLLM V1 默认开启 Automatic Prefix Caching（关闭：--no-enable-prefix-caching）；SGLang 默认开启 RadixAttention（关闭：--disable-radix-cache）。两边都是默认复用，差在索引结构与调度重心，不是「手开 vs 自动」。混合模型还要在块边界上留下 GDN 检查点。v0.18.1 开着 APC 且模型支持时，默认常常是 all。v0.32 起去掉 all：开着 APC 用 align，关掉用 none。

量化

分清三口径，别混为一谈：Weight-only（如 W4A16 / AWQ / GPTQ：权重低压，激活多为 16bit）；W8A8（如 FP8/INT8 权重与激活量化；FP8 也可能仅用于权重或 KV）；KV quant（压 KV cache）。都换显存与带宽，需业务验收质量。T4 不支持 FP8 W8A8 加速（见官方兼容表）；这张卡的 9B 演示用 W4A16。

Speculative decoding

草稿模型一次提议多个 token，目标模型在同一步里验证，接受则少做几次逐 token 的 decode。验证步往往只有几行，所以它和第 14 节的小 batch 延迟内核是同一类负载：算术少，启动和通信的空等占比高。T4 实验不启推测解码，也不装那些插件。

并行一句话：TP 切层内权重；PP 按层切；DP 复制整份模型抬吞吐；EP 切 MoE expert。注意力数据并行是另一旋钮：多张卡上把不同请求的注意力分开算，份数不等于模型副本数。阅读服务参数时找这个份数（新文档写作 --attn-dp-size），不要把旧的布尔开关当成还要手写的步骤。单张 T4 用不到。

推测解码验几个，看批大小。验证 k 个草稿就是这一步多算 k 行：带宽受限时几乎不加时间，多验划算；算力受限时每行都要付钱，只该验接受率高的。DeepSeek 的 DSpark 让草稿模块一次并行出 5 个 token，每个带一个预测接受率；调度器按「期望接受数 ÷ 步耗时」挑全批的验证集合，步耗时来自启动时实测的曲线。官方表格里，每 rank 16 并发时比固定验 5 个低 1.5%，96 并发时高 11%。社区常见配置是给一个 num_speculative_tokens。Qwen3.5 也带 MTP 草稿层，0.18.1 的方法表里有 qwen3_5_mtp，T4 主线不开。mtp_varlen · v0.18.1 推测解码配置

MoE 多卡时每一步要全员同步。注意力 DP 配专家 EP 时，MoE 的 all-to-all 要全员到齐，所以每一步所有 rank 一起走：DeepInfer 的调度器先让整组投票决定这一步做 prefill 还是 decode，没活的 rank 陪跑空步，步长由最慢的卡决定。EPLB 给热门专家放冗余副本、按近期统计周期性重排来压这个差距（DeepSeek 报告最慢 rank ÷ 平均约 1.05–1.09）。decode 喜欢宽 EP（DeepSeek 用 64–128 卡），因为每卡要读的专家更少。你的 9B 是稠密模型，用不到。scheduler · EPLB

SGLang 核心

RadixAttention：跨请求前缀复用

SGLang（Structured Generation Language）是面向 LLM 与多模态的高性能 serving 框架。后端的经典机制 RadixAttention：请求结束后不立刻丢弃 KV，而把 token 前缀索引进 radix 树；新请求做最长前缀匹配，命中则只算后缀。LMSYS 博客

每个小方块是一个 token。绿色是命中缓存、直接复用；铜色是要重新 prefill。缓存容量设成 20 个 token（APC 是 4 块），满了就淘汰「最久没用、也没有请求正在用」的部分。两种模式同时在跑，按钮只切换下面画的是哪一边。

普通注意力的物理 KV 可按页存放；Radix 树通常在 CPU 上维护 token 前缀到缓存的索引。分页负责存储管理，Radix 负责查找与复用，也可共享物理页。缓存命中要求连续 token 前缀相同，并满足模型、位置与相关配置约束；不是任意相同句子都能复用。Qwen3.5 还需一致的 GDN 状态检查点，不能只复用那 8 层的 KV。

把实验室里的「块 = 4」换成你的配置。vLLM 的 APC 只缓存写满的块，命中按整块计；SGLang 的 --page-size 默认是 1，按 token 命中，淘汰策略默认 LRU（服务参数文档）。第 13 节算过，vLLM 跑 Qwen3.5-9B 时块会被调到几百个 token，因为这一页还要放下 GDN 检查点。v0.18.1 开着前缀缓存且模型支持时，默认常常是 all，把日志原文抄下；none 是关掉时的结果。v0.32 起去掉 all，开着 APC 用 align，关掉用 none。判断标准仍是命中长度是否为块大小的整数倍。第 19 节的前缀实验里，共享的 system 段要比一块长得多；先在启动日志里查到实际块大小，再决定 --prefix-lines。

命中长度的通用规则：所有种类的状态都能在同一条边界拿回来的最长整块前缀。Qwen3.5 在 vLLM 上是 KV 页加 GDN 检查点。DeepSeek-V4.1-Flash 是 128 token 一块的全局 KV 加 128 窗口的滑动窗口注意力：最后那块里没有 SWA，就退一块，把最后 128 个 token 和没命中的后缀重新前向，近似补回 SWA（SWA Bounded Replay），所以 SWA 不必落盘。SWA 每层只看一个窗口，才能这样补；GDN 状态累积整段历史，只能存检查点。它的全局 KV 落在独立 SSD 集群，agent 流量保留 3 天、chatbot 7 天，任何 prefill 机器都能命中任何前缀，所以 prefill 的负载均衡不做前缀亲和。显存里的 APC / Radix 只在本实例有效，多副本时要么把相同前缀送到同一副本，要么接受命中率下降。DeepInfer Q&A · 模型卡

进阶对照

主线做完之后，怎样读 SGLang

先在 vLLM 上做完前缀对照，再读 SGLang。本项目没有 T4 + Qwen3.5-9B W4A16 的 SGLang 配方。不能拿「某版本支持 T4」证明这份 checkpoint 的 GDN、量化和 FP16 都能加载。安装页上的 BF16、262144 上下文命令不要照抄。

先在已跑通的 vLLM 上完成前缀对照，并留下这些数：
  1. 停服务并以 PREFIX_CACHE=0 启动，固定长 system 前缀，只改 user 后缀。
  2. 预热后顺序请求；用 --shared-prefix 保存 TTFT。同时记下容器启动到 /v1/models 的墙钟时间，不要混进 TTFT。
  3. 停服务，以 PREFIX_CACHE=1 重启同一 checkpoint，再预热、测量。
  4. 从启动日志抄下块大小 N、Mamba/GDN 模式原文、激活 / KV dtype、注意力后端。v0.18.1 开着前缀缓存且模型支持时，默认常常是 all，照抄；none 表示没有这份检查点。v0.32 起开 APC 用 align，关掉用 none。
  5. 从 /metrics 抄下 prefix cache 的 queries 与 hits，用原字段名。命中长度应是 N 的整数倍。没有命中或请求短于 N，就记成这次没有复用。

然后只回答四个是否：加载器能否读这份 W4A16、能否强制 FP16、GDN 在 SM75 上有没有内核、上下文能不能先收到 4096。有一项不成立就停。若某一版确实用同一 checkpoint 起了服务，用下面的客户端，并只比三段：就绪时间、同一条 shared-prefix 的 TTFT 与命中、并发升高时 TTFT 和 token 间隔谁在变。

  --model YOUR_SERVED_MODEL_ID \
  --requests 1 --warmup 0 --show-output

快加载器改变的是就绪时间。SGLang 的 InstantTensor 在 DeepSeek-R1、8×H200 上有一组从 160 s 到 15.3 s 的测量，并称为大约 10 倍；拿来理解「加载和 TTFT 要分开」，不要当成 9B 在 T4 上的预期。PD 分离改变的是长 prefill 会不会挡住 decode，单卡做不到；你在第 14 节看到的干扰就是它要拆开的那件事。低延迟插件要 GB300 / MI355X 这一档，不要在 T4 上打开。两引擎都用同一 checkpoint、精度、长度、采样和前缀跑通之前，不比吞吐。

问答

推荐同学常问

Q. 我们该先上 vLLM 还是 SGLang？

两周内要稳妥上线通用开源模型 → 多数团队先 vLLM。流量明显共享 system/工具定义 → 必须认真测 SGLang。最终用自家回放数据说话。

Q. slang 是另一个项目吗？

口语里通常就是 SGLang。若有人指别的缩写，让对方给出仓库链接再对齐。

Q. 和排序服务共用 GPU 行吗？

技术上可能，运维上很痛：KV 膨胀会挤占，延迟抖动互相放大。生产更常见是推理池独立，经网关调用。

Q. 为什么榜单和我压测差很多？

长度分布、前缀重叠、是否流式、精度、是否默认配置都不同。无共享前缀的榜会低估 radix/prefix。

Q. OpenAI SDK 能直接打两家吗？

可以。改 base_url 与 model 名即可。注意 chat template / tool call 细节仍可能有差异，以各引擎文档为准。

Q. 这一页把推理讲浅了吗？

每个机制都尽量落到可算的数上：注意力拆成五步并给出 GQA 的缓存倍数；采样可以调参看分布；第 7 节按 zero-to-sglang 第 4 章算 KV，并加上 GDN 状态和 9.35 GiB 权重；第 8 节用 T4 的 65 TFLOPS / 320 GB/s 推出 prefill 与 decode 的瓶颈；连续批处理与 Radix/APC 都是逐步模拟。矩阵手算和章末题在 zero-to-sglang 原文；想写成代码，接着读该仓库 Part II 的前向、KV 实现和 RadixAttention。

Q. 屋顶线算出来的 tok/s 能当性能指标吗？

不能。它是只看带宽和峰值算力的理论上界，没算反量化、kernel 效率、调度和 Python 开销，也没在 T4 上实测。用法是先预测，再拿实测对比：差得越多，越值得去 profile。

Q. Qwen3.5 支持 262144，T4 为什么先用 4096？

模型能力上限不等于本机可承载容量。4096 是保守实验值，不是模型原生上限；输入与输出合计不能超过它。9B BF16 仅按 9B×2 字节估算就约 18GB，超过 T4 标称容量，尚未计算视觉部分与运行开销。因此主线选 W4A16；更长窗口要实测预算后再增加。

Q. T4 实验要换成更新的引擎镜像吗？

不用。启动命令保持指南里的 v0.18.1。这一版开着 APC 时，模式原文常常是 all；要带走的是 v0.32 起开 APC 用 align、关掉用 none。块大小、三种 dtype、就绪时间和 TTFT、prefill 与 decode 的冲突，在第 7、8、13、14 节和实验第 6 步里观察。换镜像是另一组实验，结果分开记。

Q. 关掉思考会改变模型吗？

不会更换 checkpoint。模板的 enable_thinking 控制生成方式，reasoning parser 负责解析字段，二者不同。短窗口不自动让短问题变差；当实际推理/回答需要更长输出却被 max_tokens 或上下文截断时，结果才可能不完整。
