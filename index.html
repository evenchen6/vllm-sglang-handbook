02

命名

四个词指的是四件事

口语里的 transformer / transformers / vLLM / SGLang 经常被揉成一件事。学习时拆开，代码才对得上。

Transformer

一种神经网络结构。核心是注意力层。原始论文：Vaswani 等人 2017 年 Attention Is All You Need。

Transformers（库）

Python 库，仓库 huggingface/transformers。模型定义框架：配置、模型类、预处理器，加上 Pipeline 与 Trainer。

vLLM

推理与服务引擎，仓库 vllm-project/vllm。起源于 UC Berkeley；以 PagedAttention、连续批处理与 OpenAI 兼容服务闻名。docs.vllm.ai

SGLang

高性能 serving 框架，仓库 sgl-project/sglang。以 RadixAttention 前缀复用与结构化生成前端闻名。docs.sglang.ai / docs.sglang.io

和 checkpoint 的差别：架构是层的定义，checkpoint 是训练好的权重。「模型」两者都可能指。BERT 是架构，bert-base-cased 是一组权重。config.json 描述架构超参，权重文件才是 checkpoint。
03

迁移

推荐后台 ↔ 推理概念对照

把推理引擎想成「会说话的排序服务」：输入是 token 序列，输出是逐 token 生成；瓶颈常常在显存与调度，而不只是算力够不够。

推荐后台熟悉的概念LLM 推理中的对应备注
QPS / 吞吐throughput（req/s 或 tok/s）更常看 token/s；长输出时 req/s 会掉
p99 端到端延迟拆成 TTFT + 后续 token 延迟「多久开始吐字」与「吐字顺不顺」
批处理（mini-batch）continuous batching请求可中途加入、完成即离开
特征缓存 / Embedding 缓存KV cache；prefix / radix 缓存KV 在 GPU 上随序列与并发增长
分片 / 副本TP / PP / DP / EPTP 切层内运算；DP 像多副本抬吞吐
限流 / 熔断 / 排队max_num_seqs、队列、503、preemption显存不够会抢占重算
多租户 / 路由模型路由、LoRA、served-model-name网关 AB / 金丝雀与推荐一致
冷启动权重加载、CUDA graph / compile首次与重启后 TTFT 差一截
特征维 / 序列长度context length（max model len）超长上下文直接吃显存并抬 TTFT
一句话心智模型：推荐打分多为固定计算图；LLM decode 是自回归循环，历史 KV 常驻显存。并发越高、上下文越长，越容易撞显存墙。
04

结构

一块 Transformer 里有什么

原论文堆叠编码器与解码器块。今天的解码器-only LLM（GPT、Llama、Qwen）主要是「自注意力 + 前馈」反复堆叠，外加嵌入与输出头。先拖图，数字和名字都标在图上。

整个模型的一次前向与采样 · 拖动查看 1 / 6

整模型先查 Embedding，再经过多个 Decoder Block，最后经 Norm 与 LM Head 得到 logits；采样才选出新 token。Embedding 与 LM Head 不在每个 Block 里重复。引擎优化这些前向与请求如何共享 GPU。

单个常见 Pre-Norm Block 内部位置与作用
Norm → 注意力 → 残差相加Q/K/V 来自本层输入；RoPE 在 Q/K 上引入位置旋转
Norm → FFN → 残差相加逐位置变换；另有这一条残差支路

这是常见解码器结构的教学骨架，不是 2017 Post-Norm 的逐行实现，也未展开 Qwen 的 gate。Qwen3.5 的 GDN 层要用递推状态替代普通全注意力的 KV 历史；下面单独画出层排布。

Qwen3.5-9B 的 32 层

图上的排布来自模型卡。Qwen3.5-9B 写明 32 层，是 8 组「3 × Gated DeltaNet → FFN，再 1 × Gated Attention → FFN」。金黄色是线性递推，不按 token 增长 KV；铜色才是上面那块全注意力。8 层全注意力、每层 4 个 KV 头、头维 256，也是卡片上的数字。
05

计算

缩放点积注意力

注意力让每个位置从其他位置收集信息。查询 Q、键 K、值 V 由输入线性投影得到。输出是值向量的加权和，权重来自查询与键的相似度。

Attention(Q, K, V) = softmax(QKᵀ / √dₖ) V

除以 √dₖ 防止维度变大时点积过陡。多头注意力把计算做 h 次再拼接投影。Vaswani et al., 2017

拖动查询位置 · 格子里的数是当场算的

因果掩码：解码器-only 生成时，位置 i 只能看见 ≤ i 的 key。这就是「从左到右吐字」的数学来源。
05A

把链路串起来

从 token id 到下一个 token

Token 不等于一个汉字或一个单词。Tokenizer 把字符串切成词表中的 token id；chat template 把 system/user/assistant 角色与控制符序列化。前缀缓存比较的是这些实际 token 的连续前缀，不是语义相似度。

数据普通批次形状含义
input_ids[B, S]B 个序列，每条 S 个已知 token
hidden states[B, S, D]查表并逐层变换后的向量
Q[B, Hq, S, d]各注意力头的查询
K / V（普通 GQA）[B, Hkv, S, d]KV 头可少于 Q 头，因此计算器用 Hkv
logits[B, S, Vocab]每个位置预测其后一个 token 的分数；引擎可只算需要的位置

生成下一个 token 时取最后位置的 logits，经过温度、top-k/top-p 等采样规则选出一个 id，再送回下一次前向。LM Head 产生分数，softmax/采样形成选择；它不是直接拼出一句话。

为什么不缓存 Q？普通因果自注意力生成后续 token 时，用新的 Q 查询已有 K/V；过去的 Q 不参与这个新位置的计算。每层缓存自己的 K/V。GDN 则保留卷积与递推状态，不逐 token 保留完整 K/V 历史。

不使用 KV cache 的朴素循环会重复计算历史位置的投影、注意力和 FFN；使用 cache 后，decode 仍需读取历史 KV 做注意力，不是「旧 token 完全不再计算」。形状、移位预测与可选的 Qwen3.5 前向观测见 原理补充。

06

家族

编码器 / 解码器 / 编解码器

Encoder-only

BERT 一类。双向注意力，擅长理解与分类。推理引擎主战场通常不是它。

Decoder-only

GPT / Llama / Qwen。因果自注意力，自回归生成。vLLM / SGLang 的主战场。

Encoder–Decoder

T5 / BART。编码器读输入，解码器带交叉注意力生成。服务形态更复杂一些。

07

显存

KV cache 为什么贵

对于普通因果注意力，不带 cache 的朴素生成循环会反复处理全部历史。有了 cache，decode 只计算新输入位置的投影与层变换，并用新的 Q 读取历史 K/V。KV 缓存不等于完整回答缓存。

  • 随序列长度线性增长（每层、每 token 存 K 与 V）
  • 无共享时随活跃序列数近似线性增长；前缀共享、滑动窗口与混合状态会改变实际分配
  • 输出长度事先不知道，传统连续预留易碎片与浪费。vLLM 介绍博客称早期系统因碎片与过度预留浪费约 60%–80% 相关内存。vLLM 博客 2023
KV 示意：点 token 看「已缓存」格子

推荐类比：特征缓存若按「最大特征维 × 最大并发」整块预留会浪费；后面的 PagedAttention 像把缓存切成页按需分配。

KV 字节估算器（教学公式，非引擎实测）

默认填的是 Qwen3.5-9B 模型卡上的全注意力：8 层、4 个 KV 头、头维 256。公式 2 × L × H × d × S × B × bytes 只算这些层的 K 和 V。另外 24 层 Gated DeltaNet 不按 token 这样涨。T4 标称 16GB，nvidia-smi 可见容量常约 15GiB，以实际读数为准。固定开销填 0 时只看 KV；GDN 状态、权重、临时工作区、缓存池对齐和 CUDA Graph 都不在此公式内，理论合计也不等于实测峰值。

08

两阶段

Prefill 与 Decode

一次请求 · 拖动查看前向次数

Prefill

处理 prompt 的所有新位置（可分 chunk），写入其 KV；最后一个位置的 logits 可采样出首个新 token。长 prompt 通常偏 compute-bound，是 TTFT 的一部分。

Decode

普通自回归每步输入上次采样的 token，计算它的 KV 并预测下一个。小 batch 常偏 memory-bound，涉及权重与 KV 读取；大 batch 与不同架构可能改变瓶颈。

图中 4 个 prompt 位置在第一次前向统一处理，同时得到首个新 token；新 token 自身的 KV 在下一次前向才计算。动画只表示先后顺序，不表示各阶段耗时相同。客户端 TTFT 还包含网络、排队、预处理与回传；ITL 是 token 间隔，TPOT 是请求级平均，不能把任意 SSE 分块当成单个 token。

指标含义推荐类比
TTFT到首个输出 token首包延迟
TPOT每输出 token 平均间隔流水节拍
ITL相邻输出 token 的间隔抖动敏感延迟
Throughputtok/s 或 SLO 内 req/sQPS（需声明 SLO）
压测须固定：模型、精度、长度分布、前缀是否共享、是否流式、硬件。公开榜若几乎无共享前缀，会低估 RadixAttention / prefix cache（见 Red Hat 文提醒）。

12

动机

为什么朴素 model.generate 封装还不够

朴素实现的痛

  • 固定 batch：完成的槽位难以及时补入新请求
  • 朴素 KV 预留策略可能导致碎片与浪费
  • 缺统一调度：GPU 空窗多
  • 缺生产 API：限流、流式、多租户要自己造

引擎补上的能力

  • Continuous batching
  • 分页 KV + 前缀复用
  • 张量并行 / 量化 / 推测解码
  • OpenAI 兼容 HTTP，方便接网关

这里比较的是朴素封装，非 Transformers 今天全部能力。vLLM 与 SGLang 的起源优化点不同：前者先攻「装下更多请求」，后者先攻「相关请求少算重复前缀」（Red Hat 概括）。

13

vLLM 核心

PagedAttention：把 KV 切成页

vLLM 把每条序列的 KV 切成固定大小 block，物理上不必连续，用 block table 映射——类比操作系统分页。按生成进度按需分配，减少过度预留与碎片。介绍博客

内存实验室：每格一页，每页 4 个 token

连续模式下，未用满的预留也会占格；分页模式只标记真正写入的块。颜色 A/B/C 表示不同请求。

分页式 KV 如今已成为现代引擎标配（SGLang 也采用同类思路）。vLLM 的差异化更多转向广模型 / 广硬件生态与工程完备度（见 Red Hat 2026-10-14 文）。

14

调度

连续批处理时间线

固定批处理：组好的一批通常一起推进，完成的槽位不及时补入新请求（不要求永远等满 N 条才启动）。Continuous batching：在调度步边界重组 batch——新请求可加入，完成即离开，并不是在一个 GPU kernel 运行到一半插入。vLLM、SGLang、TensorRT-LLM 都以它为核心能力之一。

时间线实验室

看三条请求如何错开到达、在同一步共享 GPU，以及谁先结束离开 batch。

  • Chunked prefill：超长 prefill 切块，与 decode 交错，避免饿死正在吐字的请求。
  • Preemption：KV 不够时抢占并释放，之后重算。频繁抢占会伤延迟（vLLM Optimization 文档有说明）。
15

扩展

前缀缓存、量化、推测解码

Prefix caching

跨请求复用相同 prompt 前缀的 KV。vLLM V1 默认开启 Automatic Prefix Caching（关闭：--no-enable-prefix-caching）；SGLang 默认开启 RadixAttention（关闭：--disable-radix-cache）。两边都是默认复用，差在索引结构与调度重心，不是「手开 vs 自动」。

量化

分清三口径，别混为一谈：Weight-only（如 W4A16 / AWQ / GPTQ：权重低压，激活多为 16bit）；W8A8（如 FP8/INT8 权重与激活量化；FP8 也可能仅用于权重或 KV）；KV quant（压 KV cache）。都换显存与带宽，需业务验收质量。T4 不支持 FP8 W8A8 加速（见官方兼容表）；这张卡的 9B 演示用 W4A16。

Speculative decoding

草稿模型提议、目标模型验证，加速 decode。以当前版本文档为准。

并行一句话：TP 切层内权重；PP 按层切；DP 复制模型抬吞吐；EP 切 MoE expert。

GPU rank 数量（不估 OS 进程总数）
—

这里仅计 PP=1 时的 GPU rank：TP × DP。V1 另有 API、EngineCore 与执行器；单卡时 worker 可在 EngineCore 进程内执行，多卡又可能独立拉起。进程总数由实际部署决定，不能把 rank 数加 API 数当成进程总数。

在线：vllm serve

OpenAI 兼容 HTTP，默认端口常见 8000。适合接推荐网关。

离线：LLM.generate

Python 批推理。Instruct 模型需自行套 chat template 或用 llm.chat。

配置作用与本实验起步值注意

SGLang 核心

RadixAttention：跨请求前缀复用

SGLang（Structured Generation Language）是面向 LLM 与多模态的高性能 serving 框架。后端的经典机制 RadixAttention：请求结束后不立刻丢弃 KV，而把 token 前缀索引进 radix 树；新请求做最长前缀匹配，命中则只算后缀。LMSYS 博客

前缀树示意

共享 system prompt 的多会话，会在树的上层节点命中（高亮）。这是 agent / 多轮 / few-shot 场景的收益来源。

维度vLLM（起源重心）SGLang（起源重心）
KV 分配PagedAttention 降碎片高效分页 + radix 索引
跨请求复用APC 默认开启（block hash）；可 --no-enable-prefix-caching 关RadixAttention 默认开启；可 --disable-radix-cache 关
前端OpenAI API / 引擎参数OpenAI API + 结构化生成 / DSL 传统
今日两边都在吸收对方能力；选型看负载与生态，而非 2023 标签

普通注意力的物理 KV 可按页存放；Radix 树通常在 CPU 上维护 token 前缀到缓存的索引。分页负责存储管理，Radix 负责查找与复用，也可共享物理页。缓存命中要求连续 token 前缀相同，并满足模型、位置与相关配置约束；不是任意相同句子都能复用。Qwen3.5 还需一致的 GDN 状态检查点，不能只复用那 8 层的 KV。

进阶对照

SGLang 与混合模型的前缀实验

先完成 9B 在 vLLM 上的体验与计时，再挑战 SGLang。不能拿旧版本支持 T4 的结论，直接证明当前版本也能运行 Qwen3.5 的 GDN、量化与普通注意力路径。当前官方安装页与 Qwen 模型卡的主分支命令并非同一套固定环境。

本项目没有经过 T4 验证的 SGLang 9B 配置，因此不再把 BF16、262144 上下文的命令放在主线让人照抄。按 SGLang 安装文档和 Qwen3.5 模型卡选择兼容版本，记录 commit/镜像 digest。先查模型加载器、W4A16、FP16、GDN 和 SM75 支持，再调上下文。

# 仅在你已成功启动、确认 model id 的 SGLang 服务后执行
python3 examples/stream-bench.py \
  --base-url http://127.0.0.1:30000/v1 \
  --model YOUR_SERVED_MODEL_ID \
  --requests 1 --warmup 0 --show-output
先在已跑通的 vLLM 上完成前缀对照：
  1. 停服务并以 PREFIX_CACHE=0 启动，固定长 system token 前缀，只改 user 后缀。
  2. 预热后顺序请求；使用 --shared-prefix 保存 TTFT 与服务器缓存指标。
  3. 停服务，以 PREFIX_CACHE=1 重启同一 checkpoint 和配置，再预热、测量。
  4. 查看启动日志中的实际 prefix cache 与 Mamba/GDN 状态策略；开关被禁用、没有命中或不支持时，不能写成缓存有效/无效的性能结论。

跨引擎比较必须固定相同 checkpoint/revision、精度、长度分布、采样、上下文、硬件和前缀条件。不同模型只能分别记录。APC/Radix 主要节省重复 prefill，不会消除长上下文下每个新 token 读取历史的成本。

对接网关与监控最小集

边体验边学习

4–6 周：围绕 Qwen3.5 完成六个实验

周 1 · 真实问答与基本链路

先尝试 9B W4A16 非思考模式，观察中文输出。讲清 token/template、logits/采样与首 token；对照普通注意力和 Qwen3.5 的 GDN，不要求一开始推导 GDN。

周 2 · 前向与显存

可选用同代 4B 跑 5 步前向观测，比较有无 cache 的输入长度。记录 nvidia-smi 可见容量、权重、普通 KV 与 GDN 状态，区分模型加载 OOM 和运行 OOM。

周 3 · 流式与调度

同一 9B checkpoint，客户端并发 1/2/4；同步记录引擎 max-num-seqs。先排除编译与冷启动，保存 TTFT、首答案时间、E2E、输出 token/s、长度和失败数。

周 4 · 前缀开关对照

同一长 system 前缀，改变 user 后缀；顺序预热后对比 PREFIX_CACHE=0/1。确认混合状态缓存真实启用，结合缓存命中指标解释变化。

周 5 · 每次只调一项

先比较上下文 4096/8192，再比较 CUDA Graph 开关、token 预算。条件允许再做 SGLang 同模型对照；无法兼容就记录限制，不用不同模型制造引擎胜负。

周 6 · 思考与服务接入

单独开启思考，观察 reasoning 首包和最终答案时间；检查 length 截断。写网关首包/总超时、流式取消与 OOM 处理，不把短窗口直接等同于能力下降。

每次输出：环境与结果记录 + 原始 JSON + 一条由数据支持的结论。几次请求的 p95 仅供冒烟，不作为性能宣传。命令和排障见 T4 指南。

问答

推荐同学常问

Q. 我们该先上 vLLM 还是 SGLang？

两周内要稳妥上线通用开源模型 → 多数团队先 vLLM。流量明显共享 system/工具定义 → 必须认真测 SGLang。最终用自家回放数据说话。

Q. slang 是另一个项目吗？

口语里通常就是 SGLang。若有人指别的缩写，让对方给出仓库链接再对齐。

Q. 和排序服务共用 GPU 行吗？

技术上可能，运维上很痛：KV 膨胀会挤占，延迟抖动互相放大。生产更常见是推理池独立，经网关调用。

Q. 为什么榜单和我压测差很多？

长度分布、前缀重叠、是否流式、精度、是否默认配置都不同。无共享前缀的榜会低估 radix/prefix。

Q. OpenAI SDK 能直接打两家吗？

可以。改 base_url 与 model 名即可。注意 chat template / tool call 细节仍可能有差异，以各引擎文档为准。

Q. Qwen3.5 支持 262144，T4 为什么先用 4096？

模型能力上限不等于本机可承载容量。4096 是保守实验值，不是模型原生上限；输入与输出合计不能超过它。9B BF16 仅按 9B×2 字节估算就约 18GB，超过 T4 标称容量，尚未计算视觉部分与运行开销。因此主线选 W4A16；更长窗口要实测预算后再增加。

Q. 关掉思考会改变模型吗？

不会更换 checkpoint。模板的 enable_thinking 控制生成方式，reasoning parser 负责解析字段，二者不同。短窗口不自动让短问题变差；当实际推理/回答需要更长输出却被 max_tokens 或上下文截断时，结果才可能不完整。
