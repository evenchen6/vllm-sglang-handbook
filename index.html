02

命名

四个词指的是四件事

口语里的 transformer / transformers / vLLM / SGLang 经常被揉成一件事。学习时拆开，代码才对得上。

Transformer

一种神经网络结构。核心是注意力层。原始论文：Vaswani 等人 2017 年 Attention Is All You Need。

Transformers（库）

Python 库，仓库 huggingface/transformers。模型定义框架：配置、模型类、预处理器，加上 Pipeline 与 Trainer。

vLLM

推理与服务引擎，仓库 vllm-project/vllm。起源于 UC Berkeley；以 PagedAttention、连续批处理与 OpenAI 兼容服务闻名。docs.vllm.ai

SGLang

高性能 serving 框架，仓库 sgl-project/sglang。以 RadixAttention 前缀复用与结构化生成前端闻名。docs.sglang.ai / docs.sglang.io

和 checkpoint 的差别：架构是层的定义，checkpoint 是训练好的权重。「模型」两者都可能指。BERT 是架构，bert-base-cased 是一组权重。config.json 描述架构超参，权重文件才是 checkpoint。
03

迁移

推荐后台 ↔ 推理概念对照

把推理引擎想成「会说话的排序服务」：输入是 token 序列，输出是逐 token 生成；瓶颈常常在显存与调度，而不只是算力够不够。

推荐后台熟悉的概念LLM 推理中的对应备注
QPS / 吞吐throughput（req/s 或 tok/s）更常看 token/s；长输出时 req/s 会掉
p99 端到端延迟拆成 TTFT + 后续 token 延迟「多久开始吐字」与「吐字顺不顺」
批处理（mini-batch）continuous batching请求可中途加入、完成即离开
特征缓存 / Embedding 缓存KV cache；prefix / radix 缓存KV 在 GPU 上随序列与并发增长
分片 / 副本TP / PP / DP / EPTP 切权重；DP 像多副本抬吞吐
限流 / 熔断 / 排队max_num_seqs、队列、503、preemption显存不够会抢占重算
多租户 / 路由模型路由、LoRA、served-model-name网关 AB / 金丝雀与推荐一致
冷启动权重加载、CUDA graph / compile首次与重启后 TTFT 差一截
特征维 / 序列长度context length（max model len）超长上下文直接吃显存并抬 TTFT
一句话心智模型：推荐打分多为固定计算图；LLM decode 是自回归循环，历史 KV 常驻显存。并发越高、上下文越长，越容易撞显存墙。
04

结构

一块 Transformer 里有什么

原论文堆叠编码器与解码器块。今天的解码器-only LLM（GPT、Llama、Qwen）主要是「自注意力 + 前馈」反复堆叠，外加嵌入与输出头。先拖图，数字和名字都标在图上。

一块解码器 · 拖动或左右滑动 1 / 6

推理时「一次前向」就是：读已有 KV（若有）→ 算注意力与 FFN → 写出新 KV → 得到下一个 token 的分布。引擎要优化的，正是成千上万次这样的前向如何共享 GPU。

Qwen3.5-9B 的 32 层

图上的排布来自模型卡。Qwen3.5-9B 写明 32 层，是 8 组「3 × Gated DeltaNet → FFN，再 1 × Gated Attention → FFN」。金黄色是线性递推，不按 token 增长 KV；铜色才是上面那块全注意力。8 层全注意力、每层 4 个 KV 头、头维 256，也是卡片上的数字。
05

计算

缩放点积注意力

注意力让每个位置从其他位置收集信息。查询 Q、键 K、值 V 由输入线性投影得到。输出是值向量的加权和，权重来自查询与键的相似度。

Attention(Q, K, V) = softmax(QKᵀ / √dₖ) V

除以 √dₖ 防止维度变大时点积过陡。多头注意力把计算做 h 次再拼接投影。Vaswani et al., 2017

拖动查询位置 · 格子里的数是当场算的

因果掩码：解码器-only 生成时，位置 i 只能看见 ≤ i 的 key。这就是「从左到右吐字」的数学来源。
06

家族

编码器 / 解码器 / 编解码器

Encoder-only

BERT 一类。双向注意力，擅长理解与分类。推理引擎主战场通常不是它。

Decoder-only

GPT / Llama / Qwen。因果自注意力，自回归生成。vLLM / SGLang 的主战场。

Encoder–Decoder

T5 / BART。编码器读输入，解码器带交叉注意力生成。服务形态更复杂一些。

07

显存

KV Cache 的账：存什么、怎么涨、何时还

没有 KV cache，每生成一个新 token 都要对全部历史重算 K 和 V。有了它，decode 只为新 token 投影一次，再读取已经留下的 K、V。这一节按 Datawhale《zero-to-sglang》第 4 章「推理的核心数据结构」的问题来写：缓存从哪来、一次请求怎么用它、显存怎么估算、多请求时连续分配为什么撑不住。手算矩阵和章末题在原文，本页不转载正文。

留下的是每层的 K 和 V

进注意力之前，当前位置的隐藏状态各自乘出 Q、K、V。Q 表示这一步想从上下文里取什么，K 是每个历史位置用来打分的特征，V 是被加权汇总的内容。各层权重不同，所以每一层各存各的。

  • Prefill：整段 prompt 一次算出全部 token 的 Q、K、V，把每层的 K、V 写进这条请求的缓存，再做带因果掩码的注意力。预测第一个新 token 只用最后一个位置的隐藏状态。
  • Decode：采样得到的是 token id。下一步把这个 id 重新 embedding，再投影出本步的 q、k、v，把 k、v 接到历史缓存后面。q 和全部 K 做注意力，再对全部 V 加权。Q 用完即弃，下一步不会复用它。
  • 注意力之后，这个新位置还要走输出投影、残差、归一化和 FFN。整层走完，最后一层隐藏状态进 LM Head，得到词表上的 logits。
和激活的差别：中间激活算完就可以复用那块显存。KV 要跨过后面的每一个 decode step 留着，并按层、按 token 增长。所以长上下文和多请求并发时，KV 会从「比权重小」变成显存的大头。

三笔账：Prefill、单步、生成之后

各请求长度一样时，理论稠密占用是 2 × L × nkv × d × tokens × B × 每元素字节。前面的 2 是 K 和 V 两份。tokens 在 prefill 结束时是输入长度 T，生成了 l 个 token 之后是 T+l。长度不一样时，把 B×tokens 换成各请求长度之和。前缀缓存命中会让真实写入小于这个数；这里先不算命中。

一次请求的生命周期

  1. 分配。为这条请求准备可写的位置。引擎里的单位是固定大小的 block / page，按生成进度领取。
  2. Prefill 写入。prompt 每个 token 的 K、V 按层写入。前缀已经在缓存里时，命中的那段可以跳过重算。
  3. Decode 读取并追加。每步读历史 K、V，只把新 token 的 K、V 接上去。Q 不进入缓存。
  4. 结束。遇到 EOS、长度上限或取消，就减少这些页的引用计数。降到 0 归还 GPU 上的空闲池。开了前缀缓存或 RadixAttention 时，后来的请求还能命中的页会继续被引用，直到按策略淘汰。

多请求时，连续大数组为什么不够

单请求用一块连续张量存 KV，分配和追加都好讲。在线服务里请求长度和寿命都不一样，还要中途加入、完成离开。这时仍按请求划一块连续显存，会碰到四件事：

碎片和预留

按最大上下文预留，没生成的 token 先占住显存。动态分配又会留下对不上的空洞。连续区域要扩容时，还可能重新分配并拷贝。vLLM 介绍博客称早期系统因此浪费约 60%–80% 相关内存。vLLM 博客 2023

前缀存了多份

多条请求常带同一段 system prompt。各自一块缓存，就会重复保存同一段 K、V。公共前缀越长，重复占用越大。

调度和回收绑在一起

加入、退出、抢占、恢复都要同时改容量、地址和优先级。缓存一分散或需要搬家，元数据开销就上来了。

和连续批处理打架

每一步都要能插入新请求、移除已完成请求。若内核只吃规整的矩形张量，就要按最长序列填充；若为了紧凑而重排，就要 gather 或搬移。

所以 KV 不能只当成「每条请求一块越长越大的连续张量」。第 13 节的 PagedAttention 把页按需映射；第 18 节的 RadixAttention 再把相同前缀收成一棵树。物理页仍在 GPU 上，两件事解决的是不同问题。

08

两阶段

Prefill 与 Decode

一次请求 · 拖动时间

Prefill

整段 prompt 一次进模型，写满输入 token 的 KV。偏 compute-bound。决定 TTFT（多久开始吐字）。

Decode

逐 token 生成，复用并追加 KV。偏 memory-bound。决定 TPOT / ITL（吐字顺不顺）。

图里前 4 格是 prompt 的 prefill，后 4 格是逐个吐出的 decode。第 5 格出现的时刻对应 TTFT，之后每一格的间隔对应 ITL / TPOT。格子上的字是示意 token，不是某次真实生成。

下一步的输入是 token id。Prefill 用最后一个位置的隐藏状态选出第一个新 token。Decode 再把这个 token id 做 embedding，投影出新的 q、k、v，只把 k、v 追加进第 7 节的缓存。上一步的隐藏状态不会被原样送回模型。

TTFT到首个输出 token首包延迟
TPOT每输出 token 平均间隔流水节拍
ITL词间间隔抖动敏感延迟

09

库

Hugging Face Transformers 做什么

Transformers 提供模型类、配置、tokenizer / processor，以及高层 pipeline 与训练循环 Trainer。它是「定义与加载模型」的框架，不是高并发服务运行时。官方文档

你常用的三件套

AutoConfig / AutoModelForCausalLM / AutoTokenizer，或对应的具体类。

落到磁盘

config.json + 权重（safetensors/bin）+ tokenizer 文件。vLLM / SGLang 读的就是这套布局（或兼容格式）。

体验

用 Transformers 做第一次生成

适合看清「tokenizer → 模型 → 下一个 token」这条接口。高并发交给第 17 节的推理引擎。

这段不要在单张 T4 上执行。Qwen/Qwen3.5-9B 的全精度权重，vLLM recipe 标成 BF16 约 22GB，对应单张 24GB 卡。T4 是 16GB，也没有 BF16 张量核。本机可执行的演示是第 17 节的 W4A16。
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

# 接口示意。16GB T4 上请不要 from_pretrained 这份全精度权重。
# Ampere+ 常用 BF16；较新 Transformers 用 dtype=（torch_dtype 逐步弃用）
name = "Qwen/Qwen3.5-9B"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.bfloat16, device_map="auto")

messages = [{"role": "user", "content": "用一句话解释 KV cache"}]
text = tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tok(text, return_tensors="pt").to(model.device)
out = model.generate(**inputs, max_new_tokens=64)
print(tok.decode(out[0], skip_special_tokens=True))

12

动机

为什么不能只用 model.generate

朴素实现的痛

  • 静态 batch：短请求被长请求拖死
  • KV 连续预留：碎片与浪费
  • 缺统一调度：GPU 空窗多
  • 缺生产 API：限流、流式、多租户要自己造

引擎补上的能力

  • Continuous batching
  • 分页 KV + 前缀复用
  • 张量并行 / 量化 / 推测解码
  • OpenAI 兼容 HTTP，方便接网关

这四项正好对应第 7 节的连续 KV：预留浪费、前缀重复、回收复杂、变长请求难拼成矩形 batch。vLLM 与 SGLang 都在做这件事，但起源优化点不同：前者先攻「装下更多请求」，后者先攻「相关请求少算重复前缀」（Red Hat 概括）。

13

vLLM 核心

PagedAttention：把 KV 切成页

第 7 节里那块随序列变长的连续 KV，在这里被切成固定大小的 block。物理上不必连续，用 block table 映射——类比操作系统分页。按生成进度按需分配，减少过度预留与碎片。介绍博客 · vLLM 文档

内存实验室：连续预留 vs 分页

连续模式下，未用满的预留也会占格；分页模式只标记真正写入的块。颜色 A/B/C 表示不同请求。

分页式 KV 如今已成为现代引擎标配（SGLang 也采用同类思路）。vLLM 的差异化更多转向广模型 / 广硬件生态与工程完备度（见 Red Hat 2026-10-14 文）。

14

调度

连续批处理时间线

静态批处理：攒齐 N 条再算。Continuous batching：每 iteration 重新组 batch——新请求可插入，完成即离开。vLLM、SGLang、TensorRT-LLM 都以它为核心能力之一。

时间线实验室

看三条请求如何错开到达、在同一步共享 GPU，以及谁先结束离开 batch。

  • Chunked prefill：超长 prefill 切块，与 decode 交错，避免饿死正在吐字的请求。
  • Preemption：KV 不够时抢占并释放，之后重算。频繁抢占会伤延迟（vLLM Optimization 文档有说明）。
15

扩展

前缀缓存、量化、推测解码

Prefix caching

跨请求复用相同 prompt 前缀的 KV。vLLM V1 默认开启 Automatic Prefix Caching（关闭：--no-enable-prefix-caching）；SGLang 默认开启 RadixAttention（关闭：--disable-radix-cache）。两边都是默认复用，差在索引结构与调度重心，不是「手开 vs 自动」。

量化

分清三口径，别混为一谈：Weight-only（如 W4A16 / AWQ / GPTQ：权重低压，激活多为 16bit）；W8A8 / FP8（权重与激活一并低压）；KV quant（压 KV cache）。都换显存与带宽，需业务验收质量。T4 不支持 FP8 W8A8 加速（见官方兼容表）；这张卡的 9B 演示用 W4A16。

Speculative decoding

草稿模型提议、目标模型验证，加速 decode。以当前版本文档为准。

并行一句话：TP 切层内权重；PP 按层切；DP 复制模型抬吞吐；EP 切 MoE expert。

SGLang 核心

RadixAttention：跨请求前缀复用

SGLang（Structured Generation Language）是面向 LLM 与多模态的高性能 serving 框架。后端核心 RadixAttention：请求结束后不立刻丢弃 KV，而把 token 前缀索引进 radix 树；新请求做最长前缀匹配，命中则只算后缀。LMSYS 博客

前缀树示意

共享 system prompt 的多会话，会在树的上层节点命中（高亮）。这是 agent / 多轮 / few-shot 场景的收益来源。

维度vLLM（起源重心）SGLang（起源重心）
KV 分配PagedAttention 降碎片高效分页 + radix 索引
跨请求复用APC 默认开启（block hash）；可 --no-enable-prefix-caching 关RadixAttention 默认开启；可 --disable-radix-cache 关
前端OpenAI API / 引擎参数OpenAI API + 结构化生成 / DSL 传统
今日两边都在吸收对方能力；选型看负载与生态，而非 2023 标签

物理 KV 仍在 GPU 分页存放；Radix 解决「如何发现并复用前缀」，PagedAttention 解决「如何高效分配单请求 KV 页」——互补。

问答

推荐同学常问

Q. 我们该先上 vLLM 还是 SGLang？

两周内要稳妥上线通用开源模型 → 多数团队先 vLLM。流量明显共享 system/工具定义 → 必须认真测 SGLang。最终用自家回放数据说话。

Q. slang 是另一个项目吗？

口语里通常就是 SGLang。若有人指别的缩写，让对方给出仓库链接再对齐。

Q. 和排序服务共用 GPU 行吗？

技术上可能，运维上很痛：KV 膨胀会挤占，延迟抖动互相放大。生产更常见是推理池独立，经网关调用。

Q. 为什么榜单和我压测差很多？

长度分布、前缀重叠、是否流式、精度、是否默认配置都不同。无共享前缀的榜会低估 radix/prefix。

Q. OpenAI SDK 能直接打两家吗？

可以。改 base_url 与 model 名即可。注意 chat template / tool call 细节仍可能有差异，以各引擎文档为准。

Q. 这一页把推理讲浅了吗？

第 7 节对齐的是 zero-to-sglang 第 4 章：缓存的是每层 K 和 V、一次请求的生命周期、三笔显存账、连续分配在多请求下的四个问题。矩阵手算和章末题在原文链接里。想把同一条链路写成代码，接着读该仓库 Part II 的前向、KV 实现和 RadixAttention。

Q. 模型卡写了 262144，这张 T4 为什么用 8192？

262144 是 Qwen3.5-9B 的原生上下文，模型卡还建议思考任务尽量保持至少 128K。vLLM recipe 把 BF16 放在约 22GB、单张 24GB 卡上。T4 是 16GB，且不支持 FP8 W8A8 加速（见官方兼容表）。全精度和长上下文会在加载权重或分配 KV 时失败。这张卡用 W4A16 文本权重，上下文从 8192 往上试。

Q. 第一次请求为什么关掉思考？

Qwen3.5 默认先写思考再回答，短问题也会吐出很长的 reasoning，把 8192 的窗口和 T4 的剩余显存吃掉。打通接口时用 enable_thinking: false。确认服务稳定后，再单独开一次思考，并限制 max_tokens。
